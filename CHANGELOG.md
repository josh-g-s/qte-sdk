# Changelog

**Version:** 0.43

The changes in each release of qte-sdk. A release is a `vX.Y.Z` tag on `main` whose number matches `qte_sdk.__version__`. `python -m qte_sdk.update` says whether yours is the latest, and `pip install "git+https://github.com/josh-g-s/qte-sdk@v1.0.0"` installs a given release.

Changes merged since the last release are listed under "Unreleased" at the top. A release renames that heading to its number, such as `## 1.0.1`, and starts a new empty "Unreleased" section above it. (The `**Version:**` line above is this file's own revision, not the SDK's.)

## Unreleased

- On macOS and Linux, a `.env` that holds `QTE_TOKEN` or sets `QTE_URL` now gives a warning, code `QTE-DOTENV-WRITABLE`, when its group or other users can write to it, or to its folder without the sticky bit, since whoever can change it could point `QTE_URL` at a server of their own and capture the token. The warning names the paths and the `chmod go-w` command that fixes it, never the token, and the file is still used: on Linux a umask of 002 with a private group for each user makes files group-writable harmlessly. `python -m qte_sdk.token check` reports it and exits 1, and `token set` prints it after saving (#171).
- A `CONTRACT_HALTED` reject that a resume replays no longer logs `QTE-OPTIONS-CHAIN-HALTED` a second time, unnamed. A reject read again names the chain its first reading named and shares that chain's minute, so it logs at most once a minute. A reconnecting session takes a reject read on a new connection for one read before only once the new session's calendar shows the same term, so the new term's report with the same number keeps its own chain and minute; and a reject read before a calendar that names a new term stays counted (#235).
- The resting-order view (`qte_sdk.resting.RestingOrders`) now applies only executions of the team's own orders (origin `TEAM`) (#215). An execution with any other origin, including one this SDK does not know yet (such as qte-platform's coming fallback child), can no longer change or remove the entry of an order the team rests at that execution's `order_price`. Cure trades and auto-flattens never could: they are market orders and carry no `order_price`.
- The option order steps of `tests/test_conformance.py` (c to f) no longer skip when the first listed contract is reducing-only, retained, suspended or halted (#224): they take the first listed contract open to new orders, and skip, naming each contract's reason, only if none is. If another team's sell trades with a step's resting buy, the step is skipped naming the fill (contract, size and price) after market orders flatten the position, rather than failing with "no order_state within 10 s" and leaving the position open; it fails, naming the position, if flattening is not possible.
- `examples/options_bot.py` follow-ups from review. A Ctrl+C before any order is sent now says "no order was sent" and exits 0, and one while the connection closes keeps the run's printed outcome and exit status; only a second Ctrl+C while an order is being cancelled names the level where it may still rest (status 1). A `DUPLICATE_ORDER_AT_LEVEL` reject now says your team's earlier order still rests at that level and to cancel it yourself, with status 1, instead of "nothing rests". A cancel still waiting out a message-budget reject when `--drain-seconds` ends now names the reject and says to wait a minute and cancel the level yourself (with a `--drain-seconds` above 60 the run waits it out itself before it exits). New tests cover the cancel retry pacing, the SIGINT handler and the room below the asks.
- `examples/options_bot.py` second follow-ups from review (#226). The budget-reject warning and the module docstring now say that a `--drain-seconds` above 60 lets the run itself wait out the reject before it exits, not that a later run can cancel the order. New tests check that a Ctrl+C after the bot starts but before it sends an order says "no order was sent", names no resting level and exits 0; that a cancel sent again after a message-budget reject clears that reject, so the warning at the end is the plain "not confirmed" one; and that the cancel retry after `MIN_REST_VIOLATION` waits 1, 2 and then 4 grid points.
- Options: a Director's halt of an options chain is named (#216). An option book's `trading_state` can be `OPTION_HALTED` (4), which `qte_sdk.options.trading_state` now returns as itself rather than as `OPTION_SUSPENDED`: a Director has halted every contract on one underlying before its split ex-date in the Winter term, so there is no wall and no matching, new orders and amends are rejected with the new reason `CONTRACT_HALTED` (1305) and cancels are accepted. The orders resting in the chain when the halt started are cancelled with the new reason `CHAIN_HALTED` (1818), and the end of the halt restores none. The mark and Greeks still publish. A session now logs the new code `QTE-OPTIONS-CHAIN-HALTED` through the `qte_sdk.options` logger, at most once a minute for each underlying (each session keeps its own minute, a `ReconnectingSession` one across its connections), when it reads either reason, naming the chain of a reject from the `new` or `amend` it sent, since a reject names no instrument, with the next step: send only cancels in that chain until its book shows another state, then place again only what that state allows. `OPTION_HALTED` is exported from `qte_sdk.options`.
- The pacing and budget warnings, and the new chain halt warning, now withhold a field that holds the token from the log record's `fields` too, not only from the message, so a handler that shows the record's fields as given never shows it. The JSON log format already did.
- The SDK reads the exchange's contract at qte-platform ebe7d705 (approved by the Head, 12 Oct 2026; `proto/upstream.toml` now records the approval). Besides the halt, it names the ticket status `TICKET_SPLIT_CANCELLED` (7): where the term posts splits, the open of a split's ex-date cancels each working ordinary ticket in the instrument, its fills standing and `stopped_mark` 0. The `qte_sdk.tickets` docstring and the quickstart say what to do, and now say that a cure ticket replacing a ticket cancels its resting children `PARENT_STOPPED`, as this contract states, rather than that none rests then. The other changes are comments only. The manifest records the commit approved too (`approved_commit`): `scripts/vendor_contract.py` keeps the approval when it re-vendors that commit and drops it, saying so, at any other; its `--check`, and CI, fail on an approval for a commit other than the pinned one.
- `tests/test_conformance.py` now checks options against a real exchange (#218), when `QTE_CONFORMANCE_OPTION_UNDERLYING` names an underlying such as SPY: the chain arrives for the first option subscribe, Greeks arrive for every listed contract, a passive limit order on a contract rests and is cancelled, and a price off the option tick and a contract that is not listed are rejected `TICK_VIOLATION` and `CONTRACT_NOT_LISTED`. With `QTE_CONFORMANCE_OPTION_MAX_ORDER` it also checks that an order of the team's maximum rests and one a contract over it is rejected `RISK_LIMIT_BREACH`. Its docstring gives the commands that start qte-platform's local options exchange on your own machine, with no AWS access, and run these steps against it.
- New worked example, `examples/options_bot.py` (#217). It reads an option underlying's listed contracts from the instruments table, subscribes to them, keeps the day's chain and the latest Greeks (`LatestGreeks`), and picks the contract in the nearest expiry open to new positions whose strike is nearest the forward of the latest valid Greeks, passing over one whose `trading_state` is not `OPTION_TRADING`. It rests one limit buy of one contract by its OCC symbol, one tick above the wall's bid, prints a reject by its reason's name, cancels the order once it rests (again at the next grid point after `MIN_REST_VIOLATION`), and on `--seconds` or Ctrl+C cancels before it exits, naming the level if the cancel is not confirmed. Linked from the quickstart, AGENTS.md and the README.
- The budget table in `docs/developing-your-algo.md` gave the October term's values (4 times the usual) as if they were the rule. It now labels them as October's and gives the usual values, which apply from the Winter term (26 October 2026): for example 1,200 messages a minute for Market Taking, not 4,800, and a burst of 200 a second, not 800. Agentic AI is closed in Winter; when it opens in Spring its cap is 120 new orders a minute, not 480.
- Chain halt warnings, follow-ups from review. A `ReconnectingSession` now gives each new connection its shared record of chain halt warnings before the connection reads anything, so a `CONTRACT_HALTED` reject or `CHAIN_HALTED` cancel the exchange sends before `session_ack` no longer logs `QTE-OPTIONS-CHAIN-HALTED` a second time within the minute. When a calendar shows the report cursor was counted in another term, the answers the record had counted by report number are forgotten with it, as they already were when the exchange closed the connection for a term change. The contract vendoring script's check that an approval names its commit has a test for an `approved_commit` recorded without `approved` (#231)

## 1.3.0

**Pace your bot.** Rejected messages count toward your team's budget window, so a bot that sends as fast as it is allowed locks itself out for as long as it keeps sending. Turn pacing on with `open_session(pacing=Pacer(Budget(...)))`, from `qte_sdk.pacing`, using your arm's values in the table under "Your message budgets" in [docs/developing-your-algo.md](docs/developing-your-algo.md#your-message-budgets). **After a budget reject,** wait a full minute before restarting your bot. **For coding agents.** `--json` on the SDK's commands and the smoke test, and `QTE_LOG_FORMAT=json` for its logs, give output to parse rather than read. Update with `python -m qte_sdk.update` and follow what it prints.

- New, opt-in: `qte_sdk.pacing` paces `new`, `cancel` and `amend` under your team's message budgets (#203). The exchange counts every one of them toward rolling windows per team, rejected ones too, so a bot that sends at its budget is rejected for as long as it keeps sending. Pass `pacing=Pacer(Budget(...))` to `open_session` or `ReconnectingSession`, with your team's values (the exchange sends none; a dated table is in docs/developing-your-algo.md), or wrap a `Connection` with `Pacer.wrap`; call sites do not change. It keeps under 80% of each cap by default (`headroom`), mirrors the exchange's sliding windows with a 50 ms guard, stamps each send when its write returns, and spreads the burst window over its quarters. It waits with `asyncio.sleep`, first come, first served, or with `on_limit="raise"` raises `PacingLimit` (`QTE-PACING-LIMIT`); `max_wait` bounds a wait. After a budget reject (1500 to 1502) it holds that window until the whole window has passed (`PacingDraining`, `QTE-PACING-DRAINING`, in raise mode), logs `QTE-PACING-REJECTED`, and, once it has watched a whole window, lowers that window's limit toward what it counted, by at most half per reject, raising it again by a tenth, and by at least a fortieth of the limit from your values, after each minute with no budget reject; a send held by a lowered limit goes as soon as a raise makes room, and `Pacer.limits` always shows the limits in force. With `on_limit="raise"`, every paced send in the second after each connect or reconnect raises, while the burst window is held. It counts the team's messages from other connections by their `accepted` reports, and a resume's replayed reports, at their receipt time; each session starts with the burst window held for a second. A wait over a second logs `QTE-PACING-HOLDING`. `send_mass_cancel` is never held. Without a pacer, a session logs `QTE-BUDGET-REJECTED` at most once a minute on a budget reject. The warnings are written from a thread of their own, never the event loop.
- JSON output for coding agents and scripts (#180). `python -m qte_sdk.token check --json`, `python -m qte_sdk.update --json` and `python examples/smoke_test.py --json` print one JSON document on stdout, with the same exit status, which it also gives as `exit_code`; the smoke test's comes at the end, on every exit, a stop by Ctrl+C or a signal included. `QTE_LOG_FORMAT=json`, read by the new `qte_sdk.logs.configure()` (which the commands and examples call, and which does nothing on import), writes the SDK's log records to stderr as one JSON object per line, with `level`, `code`, `message`, `next_step` and `fields` (`with qte_sdk.logs.configured(...):` does so for one block); the commands log SDK warnings that way too, and leave a program's own logging setup as they found it. Every line and document is ASCII, never coloured and never holds the token. A `QTE_LOG_FORMAT` other than `json` or `text` is the new code `QTE-LOG-FORMAT-INVALID`, and each command then exits 2. The automatic update check's line, when over 512 bytes (a long reason in a script other than Latin, say), is now written to a pipe or terminal without the reason, which `python -m qte_sdk.update` gives, rather than skipped. `token check` now also withholds a path that holds the token percent-encoded, and a `HistoryClient`'s DEBUG log lines withhold a request path that holds its token. docs/errors.md gives every key.

## 1.2.0

**For coding agents.** Every SDK error and warning now starts with a code, such as `QTE-TOKEN-MISSING`, and ends with what to do next; [docs/errors.md](docs/errors.md) lists them all. `python -m qte_sdk.agents` prints the guidance for coding agents. The SDK now checks for updates once a day when a session opens (set `QTE_UPDATE_CHECK=0` to turn this off). **Check one change:** `python -m qte_sdk.token check` now exits 1, not 0, when git tracks your `.env` or, on Windows, other users can open your token file; fix what it prints. **On Windows:** if your program's output is read through a pipe, as some coding-agent tools and editor consoles do, the daily update notice may be skipped, so run `python -m qte_sdk.update` yourself at the start of work. Update with `python -m qte_sdk.update` and follow what it prints.

- Every error and warning about the token, the exchange address, the `.env`, the session and the connection now has a code, such as `QTE-TOKEN-MISSING`, in its `code` attribute and at the start of its message, which has one shape: `<CODE>: <what happened>. <why it matters>. <next step>.` So the last line of a traceback says what to do. [`docs/errors.md`](docs/errors.md) lists every code with its cause and fix, and the exit codes of `token check`, `token set`, `python -m qte_sdk.update` and the smoke test in one table. Each exception keeps its base class (`MissingToken` is still a `ValueError`), and new bases `qte_sdk.errors.QteError` and `QteWarning` catch them all. The session and resume timeouts are now `qte_sdk.session.SessionTimeout`, still a `TimeoutError`. A rejection's detail from the exchange is flattened to one line in the message and kept as sent in `detail`. Exception arguments are unchanged. In the Windows warning, "A later release will refuse such a file" now comes before the fix. The git warning no longer ends with the advice to check the exchange address in a `.env` you did not create; docs/errors.md says it instead.
- The history service's, replay's and `ReconnectingSession.send`'s errors now have codes too, so every SDK error and warning has one: `QTE-HISTORY-...` for each `HistoryError` (one per subclass, such as `QTE-HISTORY-PENDING`; a `HistoryError` itself says `QTE-HISTORY-BAD-RESPONSE`, `QTE-HISTORY-UNEXPECTED-STATUS` or `QTE-HISTORY-REQUEST-FAILED`), `QTE-HISTORY-ADDRESS-MISSING` for `MissingHistoryURL`, `QTE-REPLAY-OUT-OF-ORDER` for `ReplayOutOfOrder` and `QTE-CONNECT-NO-SESSION` for `NotConnected`. `HistoryClient` now raises `qte_sdk.history.HistoryAddressInvalid` (`QTE-HISTORY-ADDRESS-INVALID`) for an address it will not use, a port that is not a number included, and `qte_sdk.history.TokenMalformed` (`QTE-TOKEN-MALFORMED`) for a token a header cannot carry; both are still `ValueError`s, and neither message shows the address or the token. Exception arguments and attributes are unchanged, except that a history error's `message` is now also withheld when, flattened to one line, it repeats part of the token; the message shows the service's text in one line. A replay's errors now leave without the traceback gathered inside the replay, as `fetch`'s do, and `HistoryClient` and `ReconnectingSession` show an address that holds the token as withheld in their `repr`. The smoke test's `connect` FAIL for a refused session or a contract version mismatch, and its `history` FAILs, now give the error's code.
- `python -m qte_sdk.token check` now exits 0 only when the token and address are found and nothing needs fixing, 1 when something must be fixed and 2 when it could not tell. **A `.env` git tracks or does not ignore, or on Windows a file other users may read, change or replace, now makes it exit 1 instead of 0**; git being unable to say whether it ignores the `.env`, or Windows not letting it fully check the token file, makes it exit 2. Sessions still only warn about these. Each finding it prints starts with its code. It withholds any path that holds the token, in any form, and it looks afresh each time it runs, whatever the program checked or read before it.
- A token pasted by mistake where a path, an address, a date, a channel or a name belongs is now withheld everywhere the SDK shows that text (#193). The Windows warning about a `.env` or the file named by `QTE_TOKEN_FILE` withholds each path, link, folder and reason it would name that holds the token, and gives no `icacls` command for one; the git warning about a `.env` withholds a path that holds the token in `QTE_TOKEN`; `replay` withholds a date or channel that holds the client's token from its `ValueError`, and raises its argument errors from a frame that no longer holds the arguments; `open_session`, and a Ctrl-C while one of these warnings is shown, leave no SDK frame holding an address or path that can hold the token; and a `HistoryClient`'s or `ReconnectingSession`'s `repr` now also finds the token in an address as its repr writes it. Text you gave, and the history service's text, is now also looked at percent-decoded. Where the SDK has no token at hand (the git warning, which runs before the `.env` is read, and a `Session`'s `repr`), and in every place above, text holding a run of 32 hex digits, the shape of the exchange's tokens, is withheld as well. Codes, exception types and arguments are otherwise unchanged; a `Connection`'s `repr` never named its address.
- The guidance for coding agents now ships inside the package: `python -m qte_sdk.agents` prints `qte_sdk/AGENTS.md` after any install of this release or later, including one from a release zip with no clone. It is the repository's AGENTS.md, which now covers setup (on Windows and without git), the token rules, updates and the message codes, with its links as full GitHub URLs; a test fails when the two copies differ. It tells coding agents to run `python -m qte_sdk.update` at the start of work and act on a `QTE-UPDATE-AVAILABLE` line, since on Windows the automatic check's warning is skipped when an agent tool reads stderr through a pipe. A new `llms.txt` at the root of the repository points coding agents to it, the quickstart and `docs/errors.md`.
- `python -m qte_sdk.update`, `check_for_update()` and the smoke test say when an update is a recommended one, and why. [`releases.json`](releases.json), at the root of the repository, lists each release with whether it is recommended, a one-sentence reason and the platforms it is recommended on; 1.1.1 is recommended on Windows. The check reads it from `main` only when the installed SDK is behind a release, with the same timeout, at most 64 KiB and no redirect, and still takes the latest release from the release tags, so when the file cannot be read the check says what it did before. `UpdateCheck` gains `recommended`, `why` and `code`.
- Behind a release, the check's message is now one line with the code `QTE-UPDATE-AVAILABLE`, such as `QTE-UPDATE-AVAILABLE: qte-sdk 1.1.0 is behind 1.1.1, a recommended update on Windows: <why>. Update with <command>.` The exit codes are unchanged.
- `open_session`, and a `ReconnectingSession` on its first connect, run the update check in the background, at most once a day on a computer (the time of the last check is kept in `qte-sdk/update-check` in the user's cache folder) and once in a program. It never delays or fails a session and never prints: when the SDK is behind a release, it logs the `QTE-UPDATE-AVAILABLE` line at WARNING through the `qte_sdk.update` logger, and otherwise says nothing. The warning is written from the check's own thread, never on the session's event loop, and with the standard stream handlers it never holds up the session or the program's exit: when stderr is a pipe or terminal that cannot take the whole line at that moment (a full pipe that nothing reads, say), or the line is over 512 bytes, it is not written there, and the next day's check says it again. On Windows, a pipe that cannot take the line, by the room it reports, is also skipped, not waited on; a pipe whose reader is already waiting for output can report none, so there the line may be skipped although it would have fit. A Windows console that is paused, or in which text is being selected, can hold the line until it resumes, as it holds the program's own output. (If something else fills the pipe in the instant between that check and the write, the line waits in the background instead; on Windows, the program's own later writes to stderr then wait behind it until the pipe is read.) Handlers the program configures (a log file, pytest's caplog, a JSON formatter) still receive it, with its `code`; a handler the SDK cannot see into, such as a custom emit or a queue listener, writes as it always has. A stderr the program has replaced or wrapped (colorama, a rich progress display, a tee) gets the same check when its `fileno()` leads to the pipe or terminal, and then can wait only if something else fills the pipe in the instant between that check and the write, or if the wrapper writes output of the program's own that it held back (rich keeps a partial line until it ends) along with it; one with no usable `fileno()` writes as it always has. It sends nothing beyond the `qte-sdk/<version>` user agent, as the command does. Set `QTE_UPDATE_CHECK=0` to turn it off. Replays and the history service never start it.
- The automatic check's warning can no longer delay the program's exit (#188). A full stderr pipe that nothing read used to leave the check's thread waiting in its write, holding the logging handler's lock, and the program then waited for it at exit; the line is now skipped there instead, as described above.
- On Python 3.14, the SDK's commands (`python -m qte_sdk.update`, `qte_sdk.token`, `qte_sdk.agents`) and the examples no longer print colour codes in their usage lines, errors and help, which Python 3.14's argparse adds on a terminal or when `FORCE_COLOR` is set; coding agents read that output as text.
- CI's Windows job checks the generated contract code's line endings with `scripts/check_contract_eol.py`, which fails if git lists none of it, misses a generated file or lists one too many, rather than passing on an empty listing. CI only, no change to the SDK itself.
- CI's Windows job runs the reconnect, resume, calendar, instruments, tickets, new message types and examples tests too: the tests' fake exchange now delivers every frame sent before it drops a connection, on Windows as elsewhere. Tests and CI only, no change to the SDK itself.

## 1.1.1

**Windows users, please update.** On Windows, cancelling a past-data fetch (`HistoryClient`), or letting `asyncio.timeout` run out on one, could freeze your whole program for up to the fetch's `timeout` (30 seconds by default) if it was downloading. Any live session in the same program stalled with it. At other points the cancelled fetch carried on in the background until `timeout` ran out. 1.1.1 ends a cancelled fetch at once on Windows, as it already did on macOS and Linux. Update with `python -m qte_sdk.update` and follow what it prints.

- On Windows, cancelling a `HistoryClient` fetch, for example with `asyncio.timeout`, now ends it at once, as the `qte_sdk.history` docs say, unless it is still looking up the service's address or opening the connection, which cannot be woken on any system. Before, a fetch cancelled while it waited on the service kept its worker thread and connection until `timeout` ran out (30 seconds by default), which could hold up the program's exit; and one cancelled while it read the data also froze the program's event loop, and so everything else the program was doing, for that long. The client now waits on the service in a way the cancel ends at once on every system. CI runs the history tests on Windows too.
- On Windows, the check of a `.env` or the file named by `QTE_TOKEN_FILE` now also reads the access list of the file's folder and the file's owner. It warns, with the same `TokenFileShared` or `AddressFileShared`, when Everyone, Authenticated Users, Users, INTERACTIVE or Domain Users may add or remove files in the folder, since they could replace a private file with one of their own, naming the folder; and when the file is owned by an account other than you, Administrators or SYSTEM. The warning suggests running `icacls` on both the folder and the file. `python -m qte_sdk.token set` and `check` report the same, and say when the folder or the owner could not be checked. It still warns rather than refuses.
- On Windows, when the `.env` or the file named by `QTE_TOKEN_FILE` is reached through symbolic links or junctions, at the file itself, at a folder on its path, or in what a link points to, the check now reads the access list and owner of the file they lead to and the list of that file's folder, and also the list of each folder that holds a link on the way, since whoever may replace any one link may point it elsewhere. The warning names each folder that broad groups may add or remove files in, and the links in it. If a link on the way cannot be followed (a loop, more than 40 links, a link that cannot be read or that points to a volume's own name, or a name on the way that cannot be looked at or is not there), the folders of the links met before it are still checked, and the same warning says the file could not be fully checked, and why, since such a link could be made to hide where it leads. A `KeyboardInterrupt`, or another interruption, raised while the SDK warns about a file that holds the token still stops the program, but no longer carries the frames or chained exceptions that held the file's text.
- On Windows, the check of a `.env` or the file named by `QTE_TOKEN_FILE` now warns, with the same `TokenFileShared` or `AddressFileShared`, when it could not see an access list it looks at: when Windows would not let it see who may open the file, or who may add or remove files in its folder or in a folder that holds a link on the way (it was denied READ_CONTROL), or when a list is in a form it cannot read. Whoever controls a list can hide it so, to hide who may open or replace the file. When the file's own list is hidden, its folders are still checked and named. Other failures to read a list still say nothing. It also compares the owner of the file's folder, and of each folder that holds a link on the way, as it does the file's, and warns when another account owns one (you, Administrators, SYSTEM and Windows' own TrustedInstaller, which owns `C:\`, are not another account), since an owner can change who may add or remove files in it. A name on the way that cannot be looked at now has its folder checked as one that may hold a link. `python -m qte_sdk.token set` and `check` report the same.
- On Windows, an owner given as LA or LG, the computer's built-in Administrator or Guest account, is resolved to that account's SID and compared with yours, so a file or folder the built-in Administrator owns is no longer reported as unchecked when you are that account, and one a Guest owns warns. An owner the check still cannot place, on the file, its folder or a folder that holds a link, makes the same warning say the file could not be fully checked. `python -m qte_sdk.token set` and `check` say a clean file is owned by you or a trusted system account: Administrators, SYSTEM or TrustedInstaller. A token on a drive that keeps no access lists, such as a FAT32 or exFAT USB stick, already warns that Everyone may read or change it; CI now checks that.
- CI runs the Windows token-file and console checks against the real Windows API, on a `windows-latest` runner. No change to the SDK itself.
- The CI guard that every Windows test ran (`scripts/check_windows_tests.py`) lists the tests with pytest's default `python_files`, `python_classes` and `python_functions`, so the project's own settings for them cannot shrink the list.
- A `.gitattributes` keeps the vendored `proto/` and `conformance/` files byte for byte on every clone, so their hash checks and `scripts/generate_contract.py` work on a Windows clone with git's default `core.autocrlf`. No change to the SDK itself.
- `scripts/vendor_contract.py` and `scripts/generate_contract.py` write LF on every system, and `.gitattributes` checks the generated `qte_sdk/contract/v1` out with LF, so vendoring or regenerating the contract on Windows leaves the tree unchanged. `scripts/generate_contract.py` also runs on Windows now: it gave protoc the proto files' paths with backslashes there, which protoc could not find. CI's Windows job regenerates the contract code to prove it. No change to the SDK itself.

## 1.1.0

Update with `python -m qte_sdk.update` and follow what it prints.

- The SDK reads the exchange's contract 11.
- `qte_sdk.tickets`, for Fundamentals tickets: a pod sends its Execution desk a ticket with `send_ticket`, cancels it with `send_ticket_cancel` and raises a cure ticket's urgency with `send_ticket_urgency`. Pods and desks pick out the exchange's answers (`ticket_accepted`, `ticket_reject`, `ticket_state`) with `is_ticket_event`, and `LatestTickets` keeps each ticket's newest state, forgetting them all on a `Disconnected` so that the states resent on the next connection rebuild it. `stopped_time_of` and `stopped_mark_of` read when a ticket stopped and the mark then, and `parent_ticket_of` names the ticket a desk's fill works.
- A desk's child order cancelled because the pod cancelled its ticket, or the mark moved beyond the ticket's limit, carries the reason `PARENT_STOPPED`. At the term's final close the children are cancelled `SESSION_CLOSE`, a child still resting when the exchange cancels a ticket itself would be cancelled with a reason from the 1800 band (today none rests then), and a Directors' handover of a working ticket cancels its outstanding children `PARENT_STOPPED` while the ticket keeps working.
- The order helpers never set the contract's new `house_team` field, which only the exchange's own sessions may send.
- The reasons `TRADING_CUTOFF` (an order message received at or after the term-end trading cutoff) and `TERM_CUTOFF` (a resting order cancelled at the cutoff) are named, instead of decoding as `REASON_CODE_UNSPECIFIED`.
- The reasons for option contracts are named: a `new` or `amend` is rejected `CONTRACT_NOT_LISTED`, `CONTRACT_SUSPENDED` or `CONTRACT_REDUCING_ONLY`, and a resting order in a reducing-only contract that would grow the position or cross zero is cancelled `CONTRACT_REDUCING_RECHECK_FAILED`. The `qte_sdk.options` docstring and the quickstart say when each applies.
- The docs say that a `reject` can carry `CURE_WINDOW`, for a new still in its order delay when a cure window opens.
- `InstrumentInfo.sector_limit` is the sector the Fundamentals sector limit counts an instrument against, and `qte_sdk.instruments.sector_of` reads it, as None when the exchange gives none.
- A `TapePrint` in live `trades` carries `feed_only`, present and true only on an option contract's residual print taken at the live print's premium because the contract had no wall on that side. Test it with `HasField("feed_only")`.
- `Origin` names `HOUSE`, the origin of the exchange's own house orders. A team's connection is never sent a report with it.
- `qte_sdk.options.is_feed_only` says whether a live tape print is an option contract's feed-only residual print; a print without the flag is an ordinary one.
- The smoke test counts the ticket states a pod or desk is sent, instead of naming `ticket_state` as a type the SDK does not know.
- The conformance session (`tests/test_conformance.py`, run only against an exchange you name) follows the published steps at v1.7: step 1a checks the `instruments` message that comes right after the calendar, step 15 checks heartbeats, the 45-second silence close, resume replay and snapshots, and a resume across an exchange restart, and step 3 accepts up to ten ladder levels a side.

## 1.0.2

Update with `python -m qte_sdk.update` and follow what it prints. If you are still on 1.0.0 from a zip, upgrade once by hand: `pip install https://github.com/josh-g-s/qte-sdk/archive/refs/tags/v1.0.2.zip`.

- On Windows, the SDK reads the access list of a `.env` that holds the token, and of the file named by `QTE_TOKEN_FILE`, and gives a `TokenFileShared` warning if Everyone, Authenticated Users, Users, INTERACTIVE or Domain Users may read or change it, naming the groups and how to fix it. It gives an `AddressFileShared` warning if one of them may change a `.env` that sets only `QTE_URL`, since a changed address could capture your token. Both are kinds of `FileShared`. `python -m qte_sdk.token set` and `check` report the same. A folder on a second drive, such as `D:\`, is usually readable, and often changeable, by every local user; keep your project under your user profile. On macOS and Linux nothing changes: a `.env` that holds the token and that other users can read is still refused, and nothing else is checked there.
- A later release will refuse, on Windows, a token or `.env` file that other users can read or change, rather than warn. (macOS and Linux refuse only a `.env` holding the token that other users can read.) If you keep your project on a shared drive, move it under your user profile now.
- On Windows, `python -m qte_sdk.token` gives PowerShell and cmd commands instead of `unset` and `export`.
- On Windows, `python -m qte_sdk.token set` refuses to run without a console, as it does without a terminal elsewhere, instead of waiting for ever with its input redirected from `NUL` (in a CI job, a scheduled task or an IDE without a console, say).

## 1.0.0

The first numbered release. It provides:

- Sessions: `open_session` authenticates with your team token, read from the environment, a token file or a private `.env`, and `ReconnectingSession` reconnects and resumes after a dropped connection.
- The exchange's calendar and instruments table: trading days and hours, each instrument's tick and lot size, and what your team may trade.
- Market data: subscribe to books, trades, marks and the market's session state, and keep the latest book of each instrument with `LatestBooks`.
- Orders: send, cancel, amend and mass cancel, read order events, and track your team's resting orders with `RestingOrders`.
- Your team's account: query positions, cash and limit use, and count fills against replies with `AccountReports`.
- Options: build and read option symbols, the day's option chain, published Greeks and each contract's trading state.
- Past market data: `HistoryClient` reads closed sessions, and `replay` runs them through your loop.
- Exact units: prices in micro-dollars and exchange timestamps, converted without `float`.
- Tools: `python -m qte_sdk.token` sets up your token, `python -m qte_sdk.update` checks for a newer release, and `examples/smoke_test.py` checks a setup end to end.
